Golf Detector — Model Release

On-device ball / club-head / hole detector for the egocentric golf CV system.

Family: golf_ego · Backbone: YOLO26s · Latest: v5 (2026-07-22) · Baseline: v2 (2026-07-10)

TL;DR

  • Per-frame YOLO26s detector for ball / club_head / hole, running on the phone's Hexagon NPU.
  • Latest v5 (3-class, 2026-07-22): ~11 ms / ~90 fps @640 on the S25; ball recall 0.80, club_head mAP50 0.895. Hole class added but not yet measurable (val has no hole labels).
  • Baseline v2 (2-class, 2026-07-10): mAP50 0.881, ~18 ms. v5 holds accuracy (ball recall +0.01, mAP steady) while adding hole; auto-mined data was excluded (it poisoned hole).
  • New 27-person / 350-min corpus split by person into train / val / test = 68 / 16 / 16 (by duration) for upcoming training + a proper hole val.

3. Overview

The Golf Detector is the per-frame object detector behind the egocentric (AR-glasses / head-cam) golf pipeline. It locates the golf ball, the club head, and the putting hole in each camera frame; those boxes feed the on-device hit counter and the live Android counter. Trained on real first-person golf footage, exported to TFLite, and run on the phone's Hexagon NPU in real time.

4. What it detects

  • ball (class 0) — the golf ball at address and during putt roll.
  • club_head (class 1) — the head of the club.
  • hole (class 2) — the cup on the green (added in the 3-class line, v3+).

5. Architecture

YOLO26s — CSP backbone → PAN neck → anchor-free detect head, 9.95 M parameters. The offline / training model uses YOLO26's end-to-end, NMS-free head (output (1, 300, 6)). For the phone we re-export the raw one-to-many head (three feature maps [1, G, G, 4+nc]) because the end-to-end head's TopK / GatherNd can't run on the NPU; threshold + per-class NMS then run in Kotlin.

6. Training data

Real egocentric footage, hand-labeled in Label Studio, then expanded: hand labels → self-pseudo-labeling → add the hole class → human-reviewed frames.

  • v2 — 1,622 hand-labeled + 4,735 pseudo-labeled (self-training).
  • v5 — the 3-class hole base + human-reviewed frames. Auto-mined data was deliberately excluded — it poisoned the hole class (a weak teacher swamped the few hand labels).

7. Deployment

Shipped as a float16 raw-head TFLite model in the android-golf app, on the Qualcomm Hexagon NPU (QNN delegate). On a Samsung Galaxy S25, v5 runs at ~11 ms / frame (~90 fps) @640; first-launch graph compile ~1.4 s. The app auto-loads the highest golf_v<N>.tflite in assets and shows the version in the HUD.

8. Version history

  • v2 — 2026-07-10 · 2-class baseline (ball, club_head); first deployed model.
  • v3 / v4 (superseded) · v3 first added hole; v4 mixed in auto-mined frames, which degraded hole → dropped.
  • v5 — 2026-07-22 · 3-class. Fine-tuned from the v3 hole model on human-reviewed frames, auto-mined excluded. No regression: ball recall +0.01, mAP steady.

9. Known limitations

  • Ball recall (~0.80) — the small ball at distance is the hardest target.
  • Hole recall unmeasured — the fixed val has no hole labels; a held-out hole val is required.
  • Ball in flight is un-trackable (motion blur); impact timing is audio-anchored, not vision.
